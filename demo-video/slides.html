One direction, one owner

Every change to a ride goes through the Trip service. It is the only writer of rides and pools, so there is exactly one place that decides who gets a seat.

State change and event commit together

The new state and its event (trip.ride.matched, trip.pool.updated) are written to outbox in the same transaction. A relay publishes them, so an update can't be lost if the broker is down.

Both sides see it

The Notification service turns events into WebSocket pushes: Nusrat sees Matched at the same moment Jashim's manifest shows her seat.

Views derive from one lifecycle status

No isLoading / isMatched flags. The UI reads a single RideLifecycleStatus, and every change goes through canTransition(), which mirrors the backend's transition table.

Commands, not direct state edits

Buttons call async commands such as reserveSeat or acceptOffer. That's the same shape as the REST calls, so each control really passes through Loading → Success / Error.

Honest note

The web demo runs on an in-browser dispatch model (sim/world.ts). It ports the backend's rules: same pickup zone, 140% detour cap, first rider needs the driver, later riders auto-join. The real backend is tested end-to-end by a script that plays the same Banani story.

Part 2 · Engineering 07 / 09

Key decision: the database refuses to oversell

services/trip/app/pooling.py · try_join()
async with rw.begin() as s:        # BEGIN IMMEDIATE: write lock
    res = await s.execute(
        update(Pool).where(
            Pool.id == opt["pool_id"],
            Pool.status == "FORMING",
            Pool.version == opt["version"],
            Pool.occupied_seats + seats <= Pool.max_capacity,
        ).values(occupied_seats=Pool.occupied_seats + seats,
                 version=Pool.version + 1))
    if res.rowcount != 1:
        continue                  # lost the race: try next / queue
services/trip/app/models.py
CheckConstraint("occupied_seats >= 0 AND occupied_seats <= max_capacity",
                name="ck_pool_capacity")   # backstop

Why not "read, then write"?

Two requests could both read "1 seat left" and both write. Here the check and the increment happen in one conditional UPDATE.

Claim A lands first

rowcount = 1
seats 2 → 3 · v7 → v8

Claim B (+340 ms)

rowcount = 0
"seat taken" → re-queued

Proven in tests/test_concurrency.py: parallel joins, and exactly one writer wins.

Part 2 · Engineering 08 / 09

The trade-off: SQLite, one file per service

We chose SQLite with a single writer per service because it makes the seat check simple and race-free, with no lock server and no extra infrastructure. The trade-off: each service runs as one container, so it can't scale out horizontally.

Gains

  • Writes are serialised (BEGIN IMMEDIATE), so the compare-and-set UPDATE is enough.
  • Zero-ops: docker compose up runs all six services with WAL-mode files.
  • The CHECK constraint still guards the data if code ever goes wrong.

Costs

  • One writer per DB file: no second replica of Trip.
  • Write throughput tops out at one machine.
  • Path to scale: Postgres per service. The same conditional UPDATE works there under row locks.
